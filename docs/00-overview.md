## 읽는 순서

`00` > `01` > `02` > `03` > `04` > `05`

무엇을(01) 만드는지 알고, 어떻게 동작하는지(02) · 어떻게 보이는지(03)를 본 뒤,
무엇부터 할지(04)와 어떤 규칙으로 짤지(05)를 확인하고 작업을 시작한다.

## 화면

화면은 4종이다.

| 화면 | 하는 일 |
|---|---|
| 목록 | 첫 화면. 저장한 회의록을 카드로 표시하고 검색으로 조회 |
| 넣기 | 녹취 파일 업로드 후 받아쓰기, 요약 · 결정사항 · 할 일로 구분 |
| 상세 | 목록에서 카드를 누르면 뜨는 가운데 겹침 창 |
| 할 일 | 여러 회의의 담당자와 기한만 모은 표 |

- 배치와 요소 이름은 `docs/화면구성.pdf` 를 따른다
- 요소의 `id` 는 `docs/화면구성.pdf` 에 적힌 그대로 쓴다. 바꾸거나 새로 짓지 않는다

## 디자인

## 왜 이렇게 나누는가 - 관심사 분리

문서도 코드처럼 **한 파일이 한 가지 관심사만** 맡게 나눈다.

- **바뀌는 이유가 다르면 파일을 나눈다.** 제품 방향(01), 동작 명세(02), 화면(03), 작업 순서(04), 코딩 규칙(05)은
  바뀌는 때와 바꾸는 사람이 다르다. 한 파일에 섞으면 하나를 고칠 때 다른 것까지 건드리게 된다
- **필요한 것만 읽는다.** API 를 고칠 때는 02 만, 화면을 고칠 때는 03 만 보면 된다
- **어긋남을 바로 짚는다.** 지시가 문서와 다를 때 "02-specs.md 의 어느 조항" 처럼 문서명과 조항으로 정확히 가리킬 수 있다
- **코드 구조와 맞물린다.** 02 는 `backend/`, 03 은 `frontend/` 와 짝을 이룬다. 문서의 경계가 코드의 경계와 같아서
  어느 문서를 고치면 어느 코드를 봐야 하는지 바로 안다
